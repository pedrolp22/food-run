# Building a release

Release ZIPs contain only the game executable, `assets/`, player instructions,
GPL license, and third-party notices. They run without the repository, compiler,
SDL installation or a separate compiler runtime installation. Graphics drivers,
a desktop display, and OpenGL 3.3 remain operating-system requirements.

## Linux

Use CMake 3.20+, Ninja, a C++20 compiler and SDL's Linux development dependencies.
Build official packages on Ubuntu 22.04 to target glibc 2.35; a binary built on a
newer distribution can require that newer distribution's glibc. SDL loads native
display/audio backends from the operating system. SDL, libstdc++ and libgcc are
linked statically; glibc and graphics/display drivers are not bundled.

```sh
cmake --preset release
cmake --build --preset release --parallel 2
ctest --preset release
cpack --config build/release/CPackConfig.cmake -C Release -B dist
python3 scripts/verify_package.py dist --smoke-test
```

SDL is fetched from a version-pinned, SHA-256-verified source archive. Network
access is required on the first configure. Caches generated by `cook_textures`
are intentionally excluded: they contain filesystem timestamps and are not
portable between machines. The game can load the original PNGs directly.

## Windows

With Visual Studio 2022's Desktop development with C++ workload and CMake:

```powershell
cmake -S . -B build/release -G "Visual Studio 17 2022" -A x64 -DSUBWAY_PORTABLE_RELEASE=ON
cmake --build build/release --config Release --parallel 2
ctest --test-dir build/release -C Release --output-on-failure
cpack --config build/release/CPackConfig.cmake -C Release -B dist
python scripts/verify_package.py dist --version-check
```

The `release` Ninja preset also works in a Visual Studio developer terminal.
MSVC release builds use the static runtime (`/MT`). MinGW release builds link SDL
and the GCC/C++/thread runtime libraries statically. A Linux MinGW-w64 toolchain
can cross-compile the Windows ZIP:

```sh
cmake -S . -B build/windows -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/mingw-w64.cmake \
  -DSUBWAY_PORTABLE_RELEASE=ON -DSUBWAY_BUILD_TESTS=OFF
cmake --build build/windows --parallel 2
cpack --config build/windows/CPackConfig.cmake -C Release -B dist
python3 scripts/verify_package.py dist
```

Cross-compilation does not run Windows tests. The GitHub Actions Windows job
builds with MSVC, runs CPU tests natively and launches the extracted executable
with `--version`. The Linux job runs CPU and graphics tests under Xvfb, then
launches the extracted game with `--smoke-test` from a different working directory.
That smoke test loads real game assets, creates an OpenGL context and renders
three hidden menu frames. Portable builds only load assets beside the executable.

## GitHub releases

History and existing branches are preserved. The release preparation commit is
named `Initial Public Release`. Do not rewrite or force-push the repository.
The project name is `foodrun`; rename the GitHub repository from `subway` to
`foodrun` before making it public, and update the local origin URL afterwards.

The workflow builds both runtime ZIPs on pushes, pull requests and manual runs.
Push a tag that exactly matches `project(foodrun VERSION ...)` to also create a
draft GitHub release containing both ZIPs, checksums, and the corresponding source:

```sh
git tag -a v0.1.0 -m "Initial Public Release"
git push origin master
git push origin v0.1.0
```

Review the draft's artifacts and publish it through GitHub Releases. Source is
archived from the exact tag with `git archive`, so local settings, build outputs
and ignored files cannot enter it. Keep the matching source archive available
alongside binaries when distributing GPL-covered builds. All third-party model
license files are preserved inside every binary ZIP.

Inspect package contents or check a locally extracted game:

```sh
python3 scripts/verify_package.py dist
./foodrun --version
./foodrun --smoke-test
```
